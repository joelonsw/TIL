## FastAPI sync/async
### 1. 이벤트 루프 하나 + 스레드풀
- FastAPI 서버는 이벤트 루프 하나. 
  - await을 만나면 그 자리 양보하고, 다른 요청 처리
  - 해당 방식으로 수천개의 요청을 적은 쓰레드로 처리
  - 따라서 이벤트 루프를 blocking 해선 안 됨
- blocking 작업은 별도 쓰레드풀로 돌려서 거기에 위임

### 2. `def` vs `async def`
- `def endpoint()`: FastAPI가 스레드풀에서 실행
  - 알아서 스레드풀로 보냄. request.get 같은 요청도 서버 안멈춤.
- `async def endpoint():`: FastAPI가 이벤트 루프에서 직접 실행
  - 이벤트 루프에서 직접 돔. 여기에서 blocking하면 서버 전체 멈춤
  - 따라서, 꼭 blocking 작업은 `await asyncio.to_thread()` 로 스레드에 던질 것
- **그럼 뭐하러 async def...?**
  - 후술할 `trace_id` 전파
  - FastAPI(starlette)의 sync용 스레드풀은 기본 40개입니다
    - async는 대기 많은 고동시성 요청에서 스레드풀 40개의 벽을 만나지 않음

### 3. `asyncio.to_thread()`
- `await asyncio.to_thread(blocking_func, *args, **kwargs)`
- blocking_func을 스레드에서 돌리고, 끝나면 결과 줘. 
- 그동안 이벤트 루프는 다른 일 해.
- async 엔드포인트 안에서 blocking 작업 돌리는 표준

### 4. BackgroundTasks
- `background_tasks.add_task(blocking_func, *args, **kwargs)`
- 오래 걸리는 blocking_func을 백그라운드에서 처리
  - sync면 쓰레드풀, async면 이벤트 루프 처리

### 5. 하나의 흐름을 쭉 유지하는 trace_id(contextvar)
- `trace_id = contextvars.bind_contextvars(trace_id=trace_id)`
- `trace_id`는 contextvar에 담김
  - contextvar는 실행 흐름에 딸린 보이지 않는 가방
  - 미들웨어가 요청 시작 때, 이 가방에 `trace_id` 넣어줌
- 로그를 찍을 때 `trace_id`를 꺼냄
- 실행 흐름을 넘어갈 때 복사가 되려면 같은 async 체인안에 있어야 함.
  - 그냥 sync 함수를 BackgroundTask에 넣으면 가방이 같이 안 따라갈 수 있음

```Python
async def load_api_docs(req, background_tasks):
    # ① async 래퍼 등록
    background_tasks.add_task(load_api_docs_async, **kwargs)
    return {"status": "accepted"}

# ② async라서 이벤트 루프 체인 유지
async def load_api_docs_async(**kwargs): 
    # ③ to_thread가 가방을 스레드로 
    await asyncio.to_thread(load_api_docs_sync, **kwargs)
```
