## FastAPI middleware

### 미들웨어란 — 요청/응답을 감싸는 껍질
- 모든 요청이 반드시 지나가는 통로 
- 요청은 바깥 → 안으로 미들웨어 통과
- 응답은 안 → 바깥으로 미들웨어 통과
- 플레이의 액션, 스프링의 필터와 동일

### 유저 커스텀 `add_middleware`의 순서
- **나중에 `add_middleware`한 것이 가장 바깥** 반영
- Starlette 구현
    ```python
    def add_middleware(self, middleware_class, ...):
        self.user_middleware.insert(0, Middleware(middleware_class, ...))   # ← 리스트 맨 앞에 삽입
    ```
    ```python
    middleware = [ServerErrorMiddleware] + self.user_middleware + [ExceptionMiddleware]
    app = self.router
    for cls, args, kwargs in reversed(middleware):    # ← 역순으로 감싸므로
        app = cls(app, ...)                            #    리스트 앞쪽이 바깥이 된다
    ```

### 실제 미들웨어 예시
```python
app.add_middleware(ResponseCodeMiddleware)   # user_middleware = [ResponseCode]
app.add_middleware(AccessLogMiddleware)      # user_middleware = [AccessLog, ResponseCode]
```
```
요청 →  ServerErrorMiddleware        (Starlette 자동, 최외곽)
        └ AccessLogMiddleware        ← 나중에 add 해서 바깥
          └ ResponseCodeMiddleware
            └ ExceptionMiddleware    (Starlette 자동, 최내곽)
              └ router (엔드포인트 함수)
```

```
router → ExceptionMiddleware → ResponseCodeMiddleware → AccessLogMiddleware → 클라이언트
                                  ↑ code 0000 주입        ↑ body 읽어 로그
```

## 그래서 이 순서여야 합니다

`ResponseCode`가 먼저 `code`를 넣고, 그다음 `AccessLog`가 body를 읽습니다. 그래서 access 로그의 `response` 필드에 `code`가 들어 있습니다:

```json
{"tag":"ACCESS","path":"/api/document/bulletin/upsert/100933","status":200,
 "response":"{\"accepted\":true,\"documents\":1,\"code\":\"0000\"}"}
```

두 줄을 바꿔 쓰면 `AccessLog`가 안쪽이 되어 **`code` 주입 전 body를 로깅**합니다. 그러면 로그만 보고는 라운지가 이 응답을 성공으로 봤는지 알 수 없게 됩니다.

## 앞서 얘기한 예외 핸들러 문제가 여기서 나옵니다

`ExceptionMiddleware`가 **최내곽**, `ServerErrorMiddleware`가 **최외곽**입니다.

- `HTTPException` / `RequestValidationError` → `ExceptionMiddleware`가 잡음 (최내곽) → 응답이 `ResponseCode`를 **통과**함
- `@app.exception_handler(Exception)` → `ServerErrorMiddleware`에 설치 (최외곽) → `ResponseCode`를 **거치지 않음**

그래서 `error_response()`가 `code`를 직접 넣어야 하고, 앞의 두 개를 지우면 `Exception` 핸들러로 안 내려온다는 게 이 구조 때문입니다.

## 한 가지 비용은 짚어두겠습니다

`BaseHTTPMiddleware`는 안쪽 응답을 스트리밍으로 다시 감싸므로 두 미들웨어 모두 `body_iterator`를 쓸 수 있습니다(그래서 `is_json_response`가 `hasattr(response, "body_iterator")`를 봅니다). 대신 **JSON body를 두 번 읽고 두 번 새 Response로 만듭니다.**

`AccessLog`가 원래도 body를 읽고 있었으니 추가된 건 한 번이고, 응답 크기가 큰 엔드포인트(`/api/document/sync` 결과 등)에서 메모리를 한 벌 더 씁니다. 지금 규모에선 문제될 수준은 아니라고 보지만, 제가 실측하진 않았습니다.
