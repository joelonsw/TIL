## 왜 VectorDB지?
- Vector: 순서가 있는 숫자의 나열
  - 임베딩 모델이 정확히 이 출력
  - 이 점들 사이의 각도를 cosine similarity로 측정
- VectorDB는 저장하고 인덱싱하는 자료형의 이름에서 따옴. 
  - 벡터라는 타입을 1급 시민으로 다루고, 벡터간 유사도 검색에 최적화된 DB
  - Relational DB 가 오히려 자료 사이의 관계에서 출발한 이름
  - DocumentDB, GraphDB 생각해보면, 자료형 기반의 DB 이름도 많음

## Retrieval Evaluation
- **필요한 이유**
  - RAG을 올바르게 설계하고 평가했는가? -> 필요한 자료를 올바르게 추출했을까?
  - Golden Dataset -> Retrieval 단계 수치화

- **RAG에서 Retrieval 품질 따로 평가하는 법**
  - `[질문] -> [Retrieval: 관련 문서 검색] -> [Generation: LLM 답변 생성] -> [답변]`
  - Retrieval 만 평가하기
    1. 상한선 문제: Retrieval이 정답 문서를 못가져 오면, Generation이 아무리 좋아도 정답 못만듦
    2. 디버깅 분리: 문서를 못찾은건지, LLM이 잘못 해석한건지 확인해야 해
       - Retrieval 문제: embedding/chunking/reranking
       - Generation 문제: 프롬프트나 모델
    3. 비용과 속도: Retrieval 평가는 LLM 호출 필요 없음. 비용 low

- **Golden DataSet**
  - (질문, 이 질문에 답하기 이해 반드시 검색되어야 하는 문서 집합)

- ***정답 문서 평가**
  - `Recall@K` = (Top-K 안에 있는 정답 갯수) / (전체 정답 갯수)
    - LLM에게 필요한 재료를 다 줬는가?
  - `Precision@K`= (Top-K 안에 있는 정답 갯수) / K
    - context에 쓰레기가 얼마나 섞였는가?
  - `MRR(Mean Reciprocal Rank)`: 첫 정답이 얼마나 앞에 있는가
    - `질문 하나의 RR = 1 / (첫 정답의 순위)` -> `MRR = 전체 질문의 RR 평균`
  - `NDCG(Normalized Discounted Cumulative Gain)`
    - 모든 정답의 순위를 반영
    - 정답의 등급 지원
    - 순위 페널티 로그 스케일

## Retrieval의 종류
- **Dense Retrieval**
  - 질문과 문서를 각각 고정길이 실수 벡터로 변환. 
  - 벡터 공간에서의 거리(유사도)로 관련성 판단하는 검색 방식
  - 장점)
    - 표현에 다양한 개념적 질문이 있다면 이를 매칭 (일상어 <-> 전문어)
  - 단점)
    - Exact match에 약점
    - 부정/미세 의미 차이 해석
    - 모델 교체시 재인덱싱 발생

- **BM25**
  - 질문의 단어들이 문서에 얼마나 의미 있게 등장하는지
    - score(query, document) -> 점수
    - 질문을 단어로 쪼개고, 각 단어가 문서에서 얼마나 중요하게 등장하는지 점수내서 합산
    - 문서 전체의 의미 이해하려는 시도 X, 순수 단어 통계 -> 자주 나오는 단어 + 희귀한 단어 기반으로 추출
  - 장점)
    - Exact Match 실패 해결
    - 도메인 용어 문자열 일치로 찾기
  - 단점)
    - 형태소 분석이 필수... 조사를 분리하지 않으면 오염됨 (ex. 배송비를, 배송비는, 배송비가...)
      - ES Nori 등으로 한번 정제해야한다고 함

- **Hybrid Search**
  - Qdrant에서 Dense/BM25 동시에 쓸 수 있음 (서로의 약점 보완)
  - 둘의 점수 체계가 달라서, 각각 알고리즘으로 회수한 문서를 어떻게 합해서 top-k를 뽑는지 정해야함
  - RRF (Reciprocal Rank Fusion) - 순위 기반 융합
    - 점수를 버리고 순위만 씀: 두 시스템 모두의 상위권이 유리해짐
    - `RRF_score(d) = Σ  1 / (c + rank_i(d))`
      - c는 관례적으로 60. 경험적으로 양쪽 합의를 중시하되 단독 1등도 살아남는 구조
  - 아키텍쳐)
    ```
                    Query
                      ↓
          ┌───────────┴───────────┐
          │                       │
    Dense Retrieval             BM25 Search
    (Vector DB, ANN)         (Inverted Index)
    Top-N (예: 50)            Top-N (예: 50)
          │                       │
          └───────────┬───────────┘
                      ↓
                Fusion (RRF)
              두 랭킹 → 하나의 랭킹
                      ↓
              후보 Top-M (예: 20)
                      ↓
                  Reranker            ← 다음 시간 주제
          (cross-encoder가 query-chunk
           쌍을 직접 읽고 재채점)
                      ↓
                최종 Top-K (예: 5)
                      ↓
                 LLM Context
    ```

  - 실습
    1. 컬렉션 스키마 새롭게 정의
       ```
       client.create_collection(
           collection_name="new_collection",
           vectors_config={"dense": VectorParams(size=3072, distance=Distance.COSINE)},
           sparse_vectors_config={"bm25": SparseVectorParams(modifier=Modifier.IDF)},
       )
       ```
    2. 적재 - 포인트마다 dense + sparse 둘다
       ```
       PointStruct(
           id=...,
           vector={
               "dense": embedding,                                # 기존 그대로
                  # SparseVector는 라틴어 기준이라, 한국어 조사/어미에 맥락 사라질수도. 형태소 분석기 필요할 수 있음
               "bm25": SparseVector(indices=[...], values=[...]), # 토큰 해시 → TF
           },
           payload=...,
       )
       ```
    3. 검색 - 서버사이드에서 RRF, FusionQuery
      ```
      client.query_points(
          collection_name=...,
          prefetch=[
              Prefetch(query=dense_embedding, using="dense", limit=20),
              Prefetch(query=sparse_query, using="bm25", limit=20),
          ],
          query=FusionQuery(fusion=Fusion.RRF),
          limit=5,
      )
      ```

## Reranker
- **개요**
  - 많이 가져와서, 다시 정밀하게 재채점 -> 앞에 몇개만 남긴다
  - Retriever가 준 후보 군 중에서 순위를 재채점

- **방식**
  - **Cross-Encoder**
    - BERT급의 작은 전용 모델. 쿼리-문서 한쌍으로 넣어 관련도 점수 추출
    - cross-encoder는 쿼리와 문서를 함께 보기 때문에 정확.
    - 다만 느려서 앞의 Retrieval에서 뽑은 친구들 대상으로만

## Context Engineering
- 컨텍스트 엔지니어링은 RAG에만 한정되지 않고, LLM에게 어떤 정보를 어떤 형태와 순서로 제공할지 전체 입력 컨텍스트를 설계하는 것 
  - Retrieval, Reranking뿐 아니라 선택, 변환, 압축, 메타데이터, 순서, 토큰 예산 관리 등을 포함

- 기본적인 RAG: 질문 → Retrieval → LLM
- 컨텍스트 엔지니어링: 질문 → Retrieval → Reranking → 선택 → 변환 → 압축 → 메타데이터/순서 조정 → Token Budget → Context → LLM
  - LLM에게 들어가는 최종 컨텍스트를 적극적으로 설계하는 구조가 된다.
